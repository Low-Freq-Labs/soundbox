## Shared-database architecture and ordinary save behavior

Sonny explicitly rejected a separate SoundBox library with an occasional save/
publish-to-rekordbox workflow. The primary store is the same native database and
its required native sidecars. SoundBox must maintain rekordbox-compatible rows,
identities, analysis, cues and update protocols when acting as the editor.

- Both apps' ordinary song playlists use native playlist IDs and membership rows.
  If sidebar groups remain, they are organization/presentation, not independent
  copies of musical membership. The ten legacy custom playlists/tree were migrated
  with exact native bindings and stable device playlist identities; do not
  duplicate them or rerun the completed upgrade.
  Derived views/provider-specific features remain views or app-specific state
  where there is no native musical-library counterpart.
- AppData retains preferences, bookmarks/identity aliases, disposable read/render
  caches, curated originals, device ownership, durable pending intents and exact
  recovery evidence. It must not become a competing canonical BPM/key/grid/cue/
  musical-metadata store. Existing local records are migration input or working
  drafts until a native transaction commits, not a permanent author-owned fork.
- An ordinary import/edit saves to the shared store automatically through the
  accepted transaction lane. No extra Save to rekordbox action, per-track sync
  button, or routine Saved to rekordbox footer. Remove messages such as Saved in
  SoundBox or Edits are saved in SoundBox and used for USB export when those
  promises no longer describe the implemented behavior. Do not remove them early
  while leaving the old local-only persistence underneath.
- Use quiet ordinary save behavior. Where waiting/failure genuinely needs user
  attention, use concise neutral progress or actionable errors; do not expose
  DB authority, writer-domain or source-publication mechanics in normal UI.
  A durable pending draft is still not a completed DB save.
- Read-only snapshots/caches remain implementation details, not a second library.
  Reconciliation compares the shared DB's verified base/current revision with a
  pending user edit. It does not arbitrate two permanently authoritative stores.
- Schema/format acceptance, safe concurrency, recovery and opaque-byte preservation
  are internal compatibility requirements. They do not imply that the database
  belongs exclusively to rekordbox. Development still requires proof before new
  native write scopes; normal proven user operations do not require repeated
  permissions or a separate publishing workflow.

This architecture is the completion criterion for the phases below. The local
manual-edit route in phase1 unblocks correction and preserves drafts during the
transition; it is not the final replacement for native persistence.
